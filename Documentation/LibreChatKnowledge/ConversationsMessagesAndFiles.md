Audit date: 2026-08-18. LibreChat source is pinned to `b2128a7d189ac020ebb6e49a57ee986e98326b77` in `/tmp/librechat-knowledge.mI6Evl/LibreChat`. ## Executive result

The web client treats a conversation as a server-owned, cursor-paginated resource and a message as a parent-linked, content-part-rich resource. Generation is a separate streaming lifecycle that can create/reconcile messages, branch from a parent, pause for interaction, and resume. Files are also server resources: upload metadata, ACL/source, deferred previews, signed/proxied downloads, usage/TTL holds, and share snapshots all matter.

The iOS app currently implements a useful cache-first subset plus generation protocol v2, staged uploads, native conversation/message history search, conversation management, whole-conversation duplication, conversation tags/bookmarks, the pinned Projects metadata/membership slice, the authenticated shared-link owner lifecycle, an owner-reachable read-only snapshot preview, direct-path conversation fork, client-local message-tree branch selection, typed HITL decisions, save-only message editing, text-only user-prompt edit-and-resubmit, bounded response regeneration, capability-gated native speech-to-text dictation, and the native Skills catalog/manual-invocation/account-activation boundary. Conversation management covers exact rename/archive/pin routes, archived cursor paging, context/swipe actions and confirmation, local-draft-safe mutations, unique local draft identity, compact unavailable fallback, partial-page preservation, and ambiguity-safe delete reconciliation. Mutation ambiguity semantics are documented and tested: rename/pin/archive use no automatic retry, transport/5xx triggers exact GET, matching authority is cached/returned, mismatch caches authority and rethrows the original error, unauthorized propagates, and 404/unconfirmable reconciliation requires refresh before retry. Tags/bookmarks add exact directory CRUD, atomic conversation replacement, raw path encoding, role/`BOOKMARKS.USE` fail-closed gating, repeated-tag OR filtering, context-menu assignment, cache updates, and offline hidden/disabled mutations; see [ConversationTagsBookmarksAndPermissions.md](ConversationTagsBookmarksAndPermissions.md). Delete treats exact GET 404 as authoritative deletion, preserves the original delete error when GET finds the conversation, and propagates GET 401 unauthorized. Profile selection is epoch/account-root fenced so stale restoration cannot install an old runtime. Authenticated live acceptance remains unproven. Continue, assistant resubmit, specialized parallel-agent branch, fork `includeBranches`/`targetLevel`/`splitAtTarget` modes, external universal-link/standalone anonymous share entry, public/ACL administration, owner directory, lossless import/export, Skill authoring/files/import, durable pending-Skill queue persistence, the authenticated file catalog/preview/download, TTS, and full-duplex voice remain absent or deferred. See [SkillsAndManualInvocation.md](SkillsAndManualInvocation.md) and [SpeechAndVoice.md](SpeechAndVoice.md). A smaller privacy-bounded transcript action is implemented: it copies or system-shares only the selected projected branch as Markdown, uses fixed user/assistant/system role labels plus cleaned visible text, skips nontext-only rows, and excludes IDs, target metadata, files, and tool payloads; individual messages expose the same cleaned-text copy boundary. Direct-path fork uses authoritative source preflight and graph validation, `.never` retry, typed preflight-vs-ambiguous handling, fresh identities, unchanged original history, cache-after-success failure classification, and a one-shot review/navigation action that proceeds only on authoritative dismissal. The message graph rejects duplicate, missing-parent, self-parent, and cyclic authoritative histories before branch-dependent send/share/edit/fork actions. Continue, assistant resubmit, and branch-inclusive fork modes remain distinct/deferred. The bounded share reader uses strict shared identities and share-scoped file paths without entering canonical cache; see [SharingAndPublicSnapshots.md](SharingAndPublicSnapshots.md).

New Chat now consumes an account-scoped authoritative `TargetCatalogSnapshot` produced from fresh authenticated config/endpoints/models plus saved-agent ACL and non-secret user-key evidence. It honors enforcement, model-selection, added-endpoint, credential and explicit-default policy; failures expose no stale choices, compatibility notices explain omissions, and a removed selection is cleared rather than silently replaced. Ordinary/project-scoped creation and saved-chat transitions share a native selector grouped into configured specs, agents, and models while preserving catalog order. Multi-term local search uses only display label/subtitle/model/endpoint/spec metadata and never raw agent IDs. For the pinned web client, `getConvoSwitchLogic` constructs a `conversationId: "new"` template and `useSelectMention` passes it to `newConversation`; only compatible modular endpoint combinations may keep added conversations (`client/src/utils/endpoints.ts:264-314`, `client/src/hooks/Input/useSelectMention.ts:40-201`, `client/src/hooks/useNewConvo.ts:293-376`). ## 1. Resource and content taxonomy

### Conversation

Web list records include at least `conversationId`, `title`, `endpoint`, `endpointType`, `model`, `agent_id`, `assistant_id`, `parentMessageId`, archive/pin/share/project metadata, tags, timestamps, and cursor paging. List filters are `limit`, `cursor`, `isArchived`, `search`, `sortBy`, `sortDirection`, `tags`, and `projectId` (`api/server/routes/convos.js:31-80`). A conversation can be unassigned to a project, archived, pinned, shared, duplicated, forked, imported, or deleted.

iOS `Conversation` stores id/title/model/updatedAt, archive/pin metadata, optional tags, and a `ConversationTarget` (endpoint routing, agent/assistant ids, parent id, spec, prompt prefix) (`Packages/LibreChatCore/Sources/LibreChatDomain/Models.swift:91-158`). Shared-link, icon, and server lifecycle fields remain outside the stable model. `LibreChatRepository.conversations` requests non-archived updated-desc pages, while the archived repository path requests archived cursor pages (`LibreChat/Data/Repositories/LibreChatRepository.swift`).

### Message and content parts

Web messages are parent-linked and may carry `text`, `content[]`, `attachments[]`, `sender`, `isCreatedByUser`, `model`, `endpoint`, `unfinished`, `error`, `tokenCount`, `quotes`, feedback, tool/agent metadata, and artifacts. Message content is not a string: text/thinking parts can be edited; artifacts can be edited by index; tool calls/results, images, citations, multimodal parts, and agent attribution may be present (`api/server/routes/messages.js:118-279`, `:360-490`).

iOS now maps text/reasoning/code/image/file/tool/unsupported content plus typed summaries, recoverable errors, audio/video, activities, title, usage, terminal metadata, and the closed LibreChat feedback model. Unknown or mismatched feedback fails closed without discarding the surrounding message. This remains package/build evidence only. Lossless attachment provenance, the full quote model, Mermaid rendering, broader code-preview/UI-resource behavior, and full agent/subagent models remain incomplete.

### Lifecycle diagram

```text
new/local composer
  -> POST generation or POST /api/messages/:conversationId
  -> persisted user message (parentMessageId)
  -> streamed assistant tail / active job
  -> terminal assistant message + title-generation cache
  -> GET messages/conversation (cursor or full route)

assistant message
  -> regenerate / edit / branch / fork
  -> new parent-linked branch or replacement generation

file picker
  -> multipart POST /api/files
  -> processing/preview pending
  -> attachment ids in message/generation payload
  -> usage/TTL hold while queued or paused
  -> authorized preview/download, or share snapshot
```

The iOS generation flow has an equivalent local optimistic user/assistant pair and resumable stream checkpoints (`LibreChat/Features/Chat/ChatModel.swift:107-210`, `LibreChat/Data/Repositories/LibreChatRepository.swift:231-430`), but it has no server mutation lifecycle around those messages.

## 3. Web behavior and reconciliation implications

The web uses TanStack Query. Message queries disable focus/reconnect/mount refetch and protect an in-flight optimistic stream: a shorter server response, a 404 during an active job, or a stale request cannot overwrite a pending assistant tail (`client/src/data-provider/Messages/queries.ts:69-151`). Branch mutation snapshots/rolls back cache, then appends the server message; artifact edit deliberately avoids optimistic cache updates because the server compares `original` content (`client/src/data-provider/Messages/mutations.ts:1-84,87-168`). Conversation archive removes from active pages and inserts into archived pages; pin/update mutate all list caches; sharing flips `isShared` locally then refetches because create/update does not echo snapshot settings (`client/src/data-provider/mutations.ts:1-230`).

The iOS cache is namespaced by profile/account and stores whole encoded conversations/messages/drafts/uploads in SwiftData (`LibreChat/Data/Persistence/CacheStore.swift:80-195,292-452`). It safely reconciles full vs partial conversation pages, but message saves replace a conversation’s cached message set and there is no cursor/message identity merge, mutation journal, server revision, attachment relation, or conflict resolution. `ChatModel` uses local ids for optimistic messages and later reloads; this is adequate for generation v2 recovery but needs identity reconciliation when server ids arrive (`LibreChat/Features/Chat/ChatModel.swift:145-210`).

Recommended native invariants:

1. Treat `(conversationId, messageId)` as the stable key; retain `parentMessageId` and branch heads, never infer a single linear list from array order.
2. Store raw/forward-compatible content parts and attachments, not only rendered text; preserve unknown parts for round-trip/export.
3. Add per-resource mutation states (`queued`, `inFlight`, `applied`, `failed`, `conflict`) and idempotency/client ids for rename/archive/pin/edit/delete/upload.
4. Never replace a longer active stream with a shorter GET; reconcile by id and parent graph after generation settles.
5. Keep file metadata and local bytes separate. Preview/download URLs are capability-scoped and may expire; do not persist signed URLs as durable ids.
6. Extend file usage before queueing and at send/resume; paused human-in-the-loop generations can outlive upload-window TTL.
7. Keep web-search, file-search, generated-file, and UI-resource attachment envelopes losslessly with message/tool provenance. Highlight and deferred-preview events update prior attachments; they are not duplicate cards.

## 4. Native UX implications

Current iOS UX provides conversation list/delete, an authoritative target-aware New Chat sheet with compatibility notices, a visible per-row overflow menu plus context/swipe actions, whole-conversation duplication with one-shot ambiguity locking, cache/offline read-only browsing, authoritative chat-routing/history gates, message loading, native Markdown/code/tool activity, stop/resume generation, one attachment menu containing Photo Library, full-screen native camera capture, and Files picker, upload progress/cancel/retry, editable offline drafts, an authenticated shared-link owner sheet, an owner-reachable read-only snapshot viewer, direct-path fork review/navigation, client-local branch sibling controls, typed HITL approval/question cards, save-only message-edit sheets, text-only prompt-resubmit sheets, selected-response feedback review/edit/clear, and accessibility streaming announcements (`LibreChat/Features/Conversations/ConversationListView.swift`; `LibreChat/Features/Chat/ChatView.swift`; `LibreChat/Features/Sharing/*`; `LibreChat/Platform/Camera/CameraCaptureView.swift`; `LibreChat/Platform/Uploads/UploadManager.swift`). Camera/upload, direct-path fork, and the newest target/hydration, branch, HITL, message-edit, prompt-resubmit, feedback, and duplication UI/model behavior are build-verified only; no Simulator or live network acceptance is claimed.

Parity UX should add:

- complete authenticated and accessibility acceptance for the visible conversation actions: rename, pin/unpin, archive/unarchive, tags, move to project, duplicate, fork from message, and delete;
- live-accept search result context, exact branch positioning, back behavior, and accessibility; the pinned message-search route is intentionally terminal (`nextCursor: null`), so do not invent pagination unless a future server advertises it;
- message actions: save-only edit of eligible text/reasoning parts, text-only user-prompt edit-and-resubmit, bounded response regeneration from a selected assistant, continue, branch, copy/export, feedback, artifact editing, tool/agent detail. Save-only edit never regenerates or resubmits; prompt resubmit preserves the original exchange and creates a sibling; response regeneration preserves the original subtree and creates a sibling only after exact target/source proof; assistant resubmit/Continue/server branch remain separate future actions;
- attachment chips with server processing/preview states, inline image/document preview, authorized download/share, retry/delete, and explicit “queued but not sent” state; native camera/photo/file capture and upload acknowledgement/reconciliation are implemented, while live processing/preview/download proof remains pending;
- complete live/accessibility proof for the owner sheet, owner-reachable snapshot, and direct-path fork; add an explicit owner publication target choice, then implement `includeBranches`/`targetLevel`/`splitAtTarget` only after authoritative contract proof, secure external universal-link/standalone anonymous entry, and fuller share-scoped file handling. Keep owner directory and public/ACL administration as separate permissioned work;
- import/export flows with size/type/error reporting;
- record-to-transcript through the native capability-gated STT sheet; play/stop TTS with voice/config capability gating remains absent.

Offline should remain read-only for server mutations; queueing a mutation requires a visible pending/conflict state and replay policy, not silent local-only success.

## Contract checklist for implementation

Before enabling a feature, test against: archived/pinned/project/tag list filters; a conversation with multiple branches; edit of text and thinking parts; unknown content part round-trip; parallel-agent branch; upload pending preview then ready/failed; expired signed URL fallback; shared conversation with and without file snapshot; queued upload across a paused generation; speech config disabled/enabled, microphone denial/interruption, STT 401/429/5xx/lost response and no-auto-send draft insertion; TTS remains explicitly unsupported; and a web edit arriving while iOS is offline.
